## Concepts

- **Proof-of-work is a lottery with a price.** A header's hash, read as an integer, must not exceed the target, and the only way to find one is to try nonces. A smaller target is a rarer win, and the work behind a target is `2^256 / (target + 1)`.
- **The most work wins, not the longest chain.** Fork choice adds up work, so a short chain of hard blocks beats a long chain of easy ones. A tie goes to the chain seen first.
- **Difficulty follows time.** Every window the target scales by the actual time over the expected time, clamped so one window cannot swing it more than fourfold.
- **A reorganization is an ordinary event.** Every branch is kept with the state it leaves, so switching is a pointer move, and the transactions of the abandoned branch go back to the pool unless the winning branch used their nonce.
- **The mempool is a market.** A bounded pool, replacement only for a higher fee, the lowest fee dropped when full, and block space sold to the best fee that can run next.
- **Nodes agree by gossip, not by a boss.** A node passes on what is new and valid, asks the sender for a parent it lacks, and ends on the same chain as everyone else however the messages are ordered. A split with equal work stays split until one block breaks the tie.
- **A majority of the hashing can rewrite recent history.** The attacker mines a secret chain, waits until the merchant has shipped, and publishes it once it holds more work. The payment disappears because its nonce was spent by the conflicting one.

## What the tests taught

- **S1:** a test helper with an unbounded loop hung for 21 minutes once a mutation removed the condition that ended it. Every search in a test now has a budget.
- **S2:** the off-by-one in Bitcoin's retarget is easy to copy by accident. Writing the expected time as `(window - 1) x interval` made the choice explicit. The clock check is not a chain rule, because a rule that depends on each node's clock would make nodes disagree about validity.
- **S3:** an index of waiting blocks kept beside the map of waiting blocks could drift from it. Deriving one from the other removed a whole class of bugs.
- **S4:** simplifying `replayChain` so genesis was treated like any block broke eight tests once the reward was above zero. Genesis is defined, not applied.
- **S5:** the first `select` retried every candidate in every round, and recovering signatures made 105 transactions take seven seconds. Stopping at the first runnable one halved the suite. A mutation that looped forever also left orphaned test processes that blocked the harness for twenty minutes, so the harness now kills the whole process group.
- **S6:** the tests showed that a node has to pass on the whole new best branch, parents first. Passing on only the block it received left peers unaware of the blocks that connected with it.
- **S7:** a number a function reports about itself cannot pin the way it counts. The confirmation count agreed with itself under both conventions, until a test compared it with the honest chain's height.
- **S8:** a sentence in the demo said "no secret chain beat the honest one", which is not what the code checks: the attacker may have led before the merchant shipped. The wording now says what is true.

## Check questions

1. **Fork choice.** Why does this chain pick the branch with the most work and not the longest one? Give two chains where they differ, say what happens when their work is equal, and explain why that tie rule leaves a split network split until the next block.
2. **Difficulty and time.** What does the retarget scale by, and what does clamping it protect against? Where does Bitcoin's off-by-one come from, and why does requiring every block to be stamped later than its parent defeat the time warp that threatens Bitcoin's retarget?
3. **Reorganization.** A merchant sees a payment in a block and ships. Name two ways it can disappear. Which transactions of the abandoned branch come back to the pool, which never do, and why?
4. **The network.** Why does a node ask the sender for the parent of a block it cannot connect and not drop the block? Why must it pass on the whole new best branch, parents first, after a reorganization? What made the tests that shuffle message order worth writing?
5. **The 51% attack.** In the demo, 50% of the hashing failed and 75% worked. Why does a majority matter more than any number of blocks? Why does the attacker publish only after the merchant has shipped? Name one thing that makes the attack harder and one thing this simulation leaves out that real chains have.

## Answers

Written by Claude at the user's request. Read them as a reference, not as a record of what the user understood.

1. **Fork choice.** The work of a block is `2^256 / (target + 1)`, and a branch weighs the sum over its blocks, so what counts is how much hashing was spent, not how many blocks it took. Difficulty can differ between blocks, because the retarget changes the target, so the longest chain need not be the heaviest. Branch A has 10 blocks at target T, each of work w, so 10w. Branch B has 6 blocks at target T/4, each of about 4w, so about 24w. B is shorter and wins. When the work is equal the branch seen first stays the tip, so a tie never causes a switch and nodes do not flip on every competing block. That is why a split network with equal work stays split: after the halves join, each side receives the other's tip, sees equal work and keeps its own. The test that does this shows it lasting until one more block gives one side more work, and then every node moves to it.
2. **Difficulty and time.** At a window boundary the new target is the old one scaled by the measured timespan over the expected one, and the expected one is `(N - 1) x interval`. Blocks that came too slowly make the timespan long and the target larger, which is easier; too fast makes it harder. The measured timespan is clamped to between a quarter and four times the expected one, so one window can change the difficulty at most fourfold. That limits what a lie about timestamps, a sudden loss or gain of hash power, or a bug can do in a single step, and lets the chain recover step by step. Bitcoin's off-by-one: a window of 2,016 blocks holds 2,015 intervals between its first and last block but is compared against 2,016 intervals of time, so by the sources the average block time ends near 10.005 minutes (I did not check Bitcoin Core's code). This chain compares `N - 1` intervals with `(N - 1) x interval`.
   *Correction to the question as first written.* It assumed that a rule which only needs a block to be later than its parent leaves room for a time warp. It does not. The attack needs the first block of a new period to be stamped earlier than the last block of the previous one, which BIP 54 forbids beyond two hours. A far-future stamp on the last block inflates one period's measured time, the timeline then snaps back, and the trick repeats. Here `checkBlock` rejects any block not strictly later than its parent, so the timeline never snaps back. The measured spans and the unmeasured gaps between windows add up to the last stamp minus the first, which is at most the real elapsed time plus the clock limit nodes apply (30 seconds here), so a majority miner cannot make blocks look slower than they were by more than that. What the chain lacks compared with Bitcoin is median-time-past, which it does not need for this, and the future limit is a check each node makes and not a rule of the chain.
3. **Reorganization.** The payment can disappear in two ways. In an honest fork, a competing branch without it gets more work, for example two miners find a block at once or a split network joins again and the other half has more work. In a double spend, an attacker with more hashing mines a secret chain with a conflicting payment from the same sender and nonce, and publishes it after the merchant has shipped. The transactions of the abandoned blocks that come back to the pool are those still valid against the new tip, with a nonce not yet used and a balance that still covers them; `applyTipChange` puts each back through the normal checks, as the partition test shows for the payment. Never back are the transactions whose nonce the winning branch used for another transaction, including the attacker's conflicting one, which fail with `nonce-mismatch` and can never be valid again, those the winning branch already included, and those the sender can no longer afford. The rewards of the abandoned blocks vanish too, and a node does not broadcast the transactions it takes back.
4. **The network.** Dropping a block whose parent is missing would stop nodes from ever catching up whenever messages arrive out of order, a node joins late or a split heals, because a chain only connects if the parent comes first and a network does not promise that. So the node keeps the block as an orphan, in a pool bounded at 100, and asks the sender for the parent, which the sender must hold since it accepted the child, and repeats down until the chain connects. That is also how a late node syncs. After a reorganization, or when an orphan connects, the new best branch can hold several blocks the peers lack. Passing on only the block that arrived would leave a peer with a child whose ancestors it must ask for one round trip at a time, so the node passes on the whole branch oldest first and each peer connects each block as it arrives. Shuffled order is worth testing because reordering is the bug class of distributed systems, it is hard to reproduce on real connections, and a seeded generator replays the same order every time. The tests checked the property that matters, that every node ends on one chain whatever the order, over several seeds with competing blocks, and writing the partition test in S6 is what exposed the missing "pass on the whole branch" in the first place.
5. **The 51% attack.** Finding blocks is a lottery weighted by share of the hashing. With a majority the attacker's expected progress per round beats the honest network's, so any deficit is eventually made up. Below a majority the chance of catching up from a deficit of z blocks falls roughly like `(q / p)^z` (the known result from Nakamoto's paper, which I neither re-read nor derived here), so the attempt is a gamble that mostly fails. Blocks count only against the other chain's work, and a short head start does not make up for a lower rate. In the demo, 50% failed within 100 rounds and 75% worked in round 13. The attacker publishes only after the merchant has shipped because the aim is to keep both the goods and the coins: published earlier, the merchant never ships, and published without more work, nothing happens, because a tie keeps the first-seen honest tip. More confirmations make it harder, since the attacker must overtake a longer lead, and so does more honest hash power. The simulation leaves out the retarget (a fixed target is the easiest case for an attacker), network delay and the stale blocks it causes, the economics (the cost of the attack, the rewards given up, the effect on the price), mining pools and a fee market.
