## Concepts

- **One value, one byte string.** A hash only means something when its input has exactly one encoding. The encoding is tag, length prefix, payload, so values cannot collide by sliding a field boundary.
- **Signatures prove who, and only who.** The sender is recovered from the signature, never stored. The signed message is domain-tagged, names its chain, and carries a nonce.
- **A Merkle root commits to a list.** Order matters, an odd leaf moves up unchanged, and a short proof shows one leaf is in the tree.
- **A header commits to everything.** Its parent, its transactions and the whole state it leaves, so the genesis hash identifies a chain, allocations included.
- **Rules are layered.** Chain structure, transaction rules and a state replay each catch different attacks.
- **Hash links are tamper-evident, not tamper-proof.** A history rewritten consistently from some block on passes every check; only consensus can choose between valid histories.

## What the tests taught

- **S1:** the unambiguity tests did not fail when the length prefix was removed, because the type tags happened to act as delimiters. A payload that looks like a tag (`"x\u0003y"`) exposed it.
- **S2:** the library hashes with SHA-256 by default, recovery accepts the high-`S` twin of a signature, and an out-of-range `r` or `s` raises a plain `Error`. Each needed its own handling and test.
- **S3:** two length checks in `verifyMerkleProof` were dead code, because the injective encoding already made them unnecessary.
- **S4:** catching every error as "malformed" would hide real bugs, so only `RangeError` and `TypeError` count as bad input.
- **S5:** without a minimum fee, anyone could create accounts for free. A transaction altered after signing recovers a stranger, so it fails for lack of funds, not as a bad signature.
- **S5b:** the genesis hash did not bind the initial allocations until the state root was added. This corrected a claim made at the S4 checkpoint.
- **S6:** the demo claimed a rewritten history without checking that it differed from the original.

## Check questions

1. **Encoding.** Why must data be encoded canonically before it is hashed, and why is a type tag alone not enough without a length prefix? Give two different values that would collide without length prefixes.
2. **Signatures.** What does each of these prevent, and what attack would be possible without it: the nonce, the chain identifier, and rejecting high-`S` signatures?
3. **Merkle trees.** How many sibling hashes prove one transaction in a block of 1,000? Why was duplicating the last leaf for odd counts dangerous in Bitcoin, and how does this tree avoid it?
4. **State.** Which properties hold after every transaction, and how do the random tests check them? How does the state root make the genesis hash identify a chain, and what can a light client do with it?
5. **Limits.** Why is a hash-linked chain tamper-evident but not tamper-proof? Which of the eleven demonstrated attacks is not caught by any layer, and what must M2 add to make it expensive?

## Answers

Written by Claude at the user's request. Read them as a reference, not as a record of what the user understood.

1. **Encoding.** A hash is a function of bytes, so two parties only agree on a hash if they produce the same bytes for the same value, and different values must give different bytes. JSON key order, float formatting and plain concatenation all break that. A type tag keeps types apart but not field boundaries: without length prefixes, `["x\u0003y", "z"]` and `["x", "y\u0003z"]` both flatten to `03 78 03 79 03 7a`, because a payload byte that looks like a tag can fake a boundary. The length prefix makes every item self-delimiting. The encoding also refuses values with no single form: JavaScript numbers, negative integers, `null` and lone surrogates.
2. **Signatures.**
   - *Nonce:* an account's transactions run once each, in order. Without it, anyone could re-broadcast Alice's signed payment and drain her.
   - *Chain identifier:* it is part of what is signed. Without it, a payment signed for one chain could be replayed on another chain that has the same accounts.
   - *Rejecting high-`S`:* `(r, s)` and `(r, n − s)` are both valid for the same message, and public key recovery accepts both. Without the rule, a third party could make a second valid signature, which changes the signed transaction's hash, so tools that track it by hash lose it. EIP-2 makes the same rule in Ethereum.
3. **Merkle trees.** `ceil(log2(1000))`, which is 10 sibling hashes, because the proof is one hash per level of the tree. Duplicating the last leaf of an odd level makes `[a, b, c]` and `[a, b, c, c]` share a root. In Bitcoin (CVE-2012-2459) that let an attacker mutate a block without changing its hash, so nodes could cache the invalid copy as rejected and then refuse the genuine block. This tree splits at the largest power of two below the leaf count and moves an odd leaf up unchanged, so those two lists have different roots, and leaves and nodes are hashed under different tags.
4. **State.** After every accepted transaction the total supply is unchanged (fees only move coins), no balance is negative, the sender's nonce is up by exactly one, and nobody else's nonce moved. A rejected transaction or block leaves the state untouched. The random tests run 300 transactions and 80 blocks, about a third deliberately wrong, against a separately written reference model, and compare every account, the supply and the verdict after each step. The state root is a Merkle root over the chain identifier and every account, sorted by address, and it sits in each header, genesis included. The genesis hash pins that header, so different allocations or a different chain identifier give a different genesis hash: the hash identifies the chain. A light client that trusts only a header can ask any node for an account and a short proof, and verify it against `stateRoot`. It cannot prove an account that does not exist.
5. **Limits.** Hash links only make a change visible against something already known, such as a trusted tip hash. Anyone can recompute hashes, so an attacker who rewrites block `k` and re-links every block after it produces a chain that is consistent from end to end, and no check can tell which history is the real one. The attack no layer catches is "Rewrite history consistently from block 2 on". M2 must add a rule that chooses between valid histories and makes producing one costly or restricted: a fork choice such as the heaviest chain, backed by proof-of-work or by signed headers from authorised producers. It also needs networking, a mempool, a block size limit and timestamp checks against a clock.
